# 如何贡献开源项目

> 来源：[Open Source Guides - How to Contribute](https://opensource.guide/how-to-contribute/)

---

## 为什么要贡献开源

### 对个人的价值

1. **提升技能**：无论是编码、设计、写作还是组织能力，开源项目都有你可以练习的任务
2. **结识同好**：开源社区让你认识志同道合的人，很多人通过开源建立了终身友谊
3. **找到导师**：在共同协作中，你既能学习也能教导他人
4. **建立声誉**：所有工作都是公开的，它们就是你的作品集
5. **锻炼领导力**：解决冲突、组织团队、确定优先级 — 这些都是领导力的体现
6. **获得成就感**：即使是小的改变，也能让你感受到对世界的影响

---

## 贡献不仅仅是写代码

> **重要认知**：开源贡献远不止写代码。事实上，项目中最容易被忽视的往往是非代码部分。

### 你喜欢规划活动？
- 组织项目的 Meetup 或研讨会
- 帮助社区成员找到合适的会议并提交演讲申请

### 你喜欢设计？
- 重构页面布局以提升可用性
- 进行用户研究来优化导航
- 制定设计风格指南
- 为项目设计 Logo 或 T 恤

### 你喜欢写作？
- 完善项目文档
- 编写使用教程
- 翻译文档到其他语言
- 策划项目的 Newsletter

### 你喜欢组织？
- 标记重复的 Issue
- 整理标签体系
- 关闭过时的 Issue
- 在新 Issue 中提出澄清性问题

### 你喜欢编码？
- 修复 Bug
- 开发新功能
- 改进自动化工具和测试
- 优化项目配置

### 你喜欢帮助他人？
- 在 Stack Overflow 或 Reddit 回答相关问题
- 在 Issue 中帮助回答问题
- 审查他人的代码
- 指导新贡献者

## 了解开源项目的结构

### 典型角色

| 角色 | 职责 |
|------|------|
| **Author** | 项目创建者 |
| **Owner** | 拥有管理权限的人 |
| **Maintainers** | 负责项目方向和组织管理的贡献者 |
| **Contributors** | 所有做出贡献的人 |
| **Community Members** | 使用项目并参与讨论的人 |

### 典型文件

| 文件 | 作用 |
|------|------|
| `LICENSE` | 开源协议（没有它就不是开源） |
| `README` | 项目说明、使用方法 |
| `CONTRIBUTING` | 贡献指南，告诉你如何参与 |
| `CODE_OF_CONDUCT` | 行为准则，营造友好环境 |

### 典型工具

- **Issue Tracker**：讨论和追踪问题
- **Pull Requests**：讨论和审查进行中的修改
- **论坛/邮件列表**：深度讨论话题
- **即时聊天**：如 Slack、Discord、IRC

## 有效沟通的技巧

### 提交 Issue 或 PR 前

1. **提供上下文**：说清楚你在做什么、遇到了什么问题
   - ✅ "当我执行 X 操作时，Y 没有按预期发生"
   - ❌ "X 坏了！赶紧修！"

2. **先做功课**：搜索 README、Issue（包括已关闭的）、文档和互联网
   - ✅ "我不确定如何实现 X，我查了文档但没找到相关说明"
   - ❌ "怎么用 X？"

3. **保持简洁**：每个贡献都需要别人花时间审查，言简意赅能提高获得帮助的概率

4. **保持公开**：不要私信维护者（安全问题除外），公开讨论让更多人受益

5. **耐心等待**：维护者可能需要时间回复，这很正常

6. **尊重决定**：即使你的贡献没被接受，也要尊重社区的选择

## 提交贡献的完整流程

### 开 Issue 的时机

- 报告你无法自己解决的错误
- 讨论高层话题或想法
- 提议新功能

**Issue 沟通技巧**：
- 如果想认领某个 Issue，先评论说明
- 如果 Issue 很旧了，先确认是否仍然有效
- 如果自己解决了问题，记得更新并关闭

### 开 Pull Request 的时机

- 提交小修复（typo、死链接、明显错误）
- 提交之前在 Issue 中讨论过的改进

**PR 最佳实践**：
1. Fork 仓库并克隆到本地
2. 创建功能分支
3. 引用相关 Issue（如 `Closes #37`）
4. 包含前后对比截图（如涉及 UI 修改）
5. 运行现有测试，确保不破坏原有功能
6. 遵循项目的代码风格
7. 不要太早投入过多时间 — 先开 Draft PR 获取反馈

## 提交后会发生什么

### 场景一：没有回应 😭

如果超过一周没收到回复：
- 在同一线程中礼貌地 @提醒 相关人员
- 仍然没有回应？不要灰心，找下一个项目

### 场景二：要求修改 🚧

这是正常的！表明维护者认真审查了你的贡献：
- 根据反馈进行修改
- 如果不确定如何改，可以请教
- 如果没时间继续，诚实告知

### 场景三：贡献被拒 👎

你的贡献可能不被接受。这没关系：
- 可以礼貌地询问原因
- 尊重维护者的决定
- 你可以 Fork 项目在自己的版本上继续

### 场景四：贡献被合并 🎉

恭喜！你已经成功为开源世界做出了贡献！
