## 引子

「Kafka 用普通磁盘做到了比很多内存系统还快的吞吐」—— 这句话第一次听到时是反直觉的。磁盘不是很慢吗？本文尝试从设计层面回答：Kafka 的性能到底来自哪里。

## 一、核心抽象：一切都是追加日志

Kafka 最根本的设计决策，是把消息系统重新定义为一个**分区的、持久化的、只追加（append-only）的提交日志**。

这个抽象带来三个直接后果：

1. 写入永远是**顺序追加**，没有随机写
2. 消费者通过 **offset** 自己定位，broker 无需维护每条消息的投递状态
3. 消息可被**重复读取**，天然支持多消费者与回溯

## 二、性能来源之一：顺序 I/O

机械硬盘的随机读写慢，是因为磁头寻道；但**顺序读写**的速度其实非常接近内存。Kafka 只做顺序追加写，因此绕开了磁盘最慢的部分。

> 经典数据：顺序写磁盘约 600MB/s，随机写可能只有 100KB/s，差距达数千倍。

## 三、性能来源之二：页缓存（Page Cache）

Kafka **不自己维护内存缓存**，而是直接依赖操作系统的页缓存：

- 写入时先进入页缓存，由 OS 决定何时刷盘
- 读取时热数据直接命中页缓存，不经过磁盘
- 好处：避免了 JVM 堆内缓存的 GC 压力，进程重启后缓存仍在

这是一个「把复杂性交给操作系统」的聪明决策。

## 四、性能来源之三：零拷贝（Zero-Copy）

传统的「读文件 → 发网络」要经历 4 次拷贝和 2 次上下文切换：

```
磁盘 → 内核页缓存 → 用户缓冲区 → socket 缓冲区 → 网卡
```

Kafka 使用 `sendfile` 系统调用（Java 的 `FileChannel.transferTo`），让数据**直接从页缓存送到网卡**，跳过用户空间：

```
磁盘 → 内核页缓存 → 网卡
```

拷贝次数从 4 次降到 2 次，这对高吞吐场景是巨大的节省。

## 五、性能来源之四：批处理与压缩

- **生产者批处理**：消息攒成批再发送，摊薄网络开销
- **压缩**：整批压缩（如 lz4/zstd），压缩率更高
- **消费者批量拉取**：一次 fetch 拉取一批

## 总结：性能是设计的副产品

Kafka 的快，不是靠某个黑科技，而是一系列**顺应硬件特性**的设计叠加：

| 技术 | 解决的问题 |
|------|-----------|
| 顺序 I/O | 绕开磁盘随机访问瓶颈 |
| 页缓存 | 免去 GC、重启缓存不丢 |
| 零拷贝 | 减少数据拷贝与上下文切换 |
| 批处理 | 摊薄单条消息的固定开销 |

**最大的启发**：当你选对了核心抽象（append-only log），性能优化就变成了"顺应硬件"的自然结果，而非对抗式的修补。这就是好架构的力量。
