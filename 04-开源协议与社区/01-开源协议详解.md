# 开源协议详解

> 来源：[Open Source Guides - The Legal Side of Open Source](https://opensource.guide/legal/)

---

## 为什么需要开源协议

默认情况下，所有创作作品受**排他性版权**保护。没有协议意味着：
- 没有人可以合法使用、复制、修改你的代码
- 即使代码是公开的（如 public repo），也不代表是开源的

> **关键区别**：GitHub 上的 public 仓库 ≠ 开源项目。Public 只允许他人查看和 Fork，但不授予使用、修改和分发的权利。

## 主流开源协议对比

### 宽松型（Permissive）

| 协议 | 核心特点 | 适用场景 |
|------|----------|----------|
| **MIT** | 最简单、最自由。只要保留版权声明，可以做任何事 | 个人项目、库、想要最大传播 |
| **Apache 2.0** | 类似 MIT，额外包含专利授权和商标保护 | 企业项目、需要专利保护 |
| **BSD 2-Clause** | 与 MIT 类似，两条限制 | 学术项目 |
| **ISC** | MIT 的简化版本 | npm 包的常见选择 |

### Copyleft 型（传染性）

| 协议 | 核心特点 | 适用场景 |
|------|----------|----------|
| **GPLv3** | 修改后的代码必须以相同协议开源 | 确保代码永远开源 |
| **AGPLv3** | GPLv3 + 网络使用也必须开源 | SaaS 服务 |
| **LGPLv3** | 弱 Copyleft，链接使用无需开源 | 共享库（如 C 库） |
| **MPL 2.0** | 文件级 Copyleft，修改的文件须开源 | 平衡自由和保护 |

### 对比总结

```
自由度从高到低：
MIT ≈ BSD ≈ ISC > Apache 2.0 > MPL 2.0 > LGPL > GPL > AGPL

传染性从强到弱：
AGPL > GPL > LGPL > MPL 2.0 > Apache 2.0 > MIT ≈ BSD ≈ ISC
```

## 如何选择协议

### 快速决策树

```
想让代码被最广泛使用？
├── 是 → MIT
└── 否 → 需要专利保护？
         ├── 是 → Apache 2.0
         └── 否 → 要求修改也必须开源？
                  ├── 是 → 包含网络使用？
                  │        ├── 是 → AGPLv3
                  │        └── 否 → GPLv3
                  └── 否 → MPL 2.0
```

### 按社区偏好选择

- **npm/JavaScript 生态** → MIT（最主流）
- **企业友好** → Apache 2.0
- **确保自由** → GPLv3
- **WordPress 插件** → GPLv2+
- **Rust 生态** → MIT 或 Apache 2.0（双协议）

## 协议实践要点

### 添加协议到项目

1. 在仓库根目录创建 `LICENSE` 文件
2. 复制协议全文（从 https://choosealicense.com 获取）
3. 填入年份和版权持有者名称

### 注意事项

1. **依赖项的协议兼容性**：
   - 你的项目协议不能比依赖项的协议更宽松
   - 例如：使用了 GPL 依赖，你的项目也必须 GPL 兼容

2. **贡献者协议（CLA）**：
   - 大多数项目不需要额外的 CLA
   - GitHub 的服务条款默认 "inbound = outbound"
   - 大型企业项目可能需要（如 Apache Foundation 的项目）

3. **更改协议**：
   - 需要所有贡献者的同意（或已有 CLA 预授权）
   - 如果从零开始还未有贡献者，添加协议等同于新建

## Creative Commons 协议（非代码内容）

用于文档、图片、数据等非代码内容：

| 协议 | 含义 |
|------|------|
| CC0 | 放弃所有权利，进入公共领域 |
| CC-BY | 署名即可自由使用 |
| CC-BY-SA | 署名 + 相同方式分享（Copyleft） |
| CC-BY-NC | 署名 + 非商业用途 |

> 注意：CC 协议不适用于软件代码。

---

## 企业开源注意事项

如果你是公司员工：
1. 确认公司的 IP 政策是否允许你开源个人项目
2. 公司项目开源需要法务部门的审批
3. 注意不要泄露商业秘密或专利信息
4. 检查第三方依赖的协议合规性
