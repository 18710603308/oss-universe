# 维护者最佳实践

> 来源：[Open Source Guides - Best Practices for Maintainers](https://opensource.guide/best-practices/)

---

## 成为维护者意味着什么

维护一个流行的开源项目，你会发现自己写代码的时间变少了，而更多时间花在：
- 回复 Issue
- 审查 PR
- 管理社区
- 文档维护

这些"非代码"工作同样重要，是项目持续发展的关键。

---

## 文档化你的流程

### 为什么文档化如此重要

- 让你的思考更清晰
- 让他人无需询问就能理解规则
- 让拒绝变得更容易（指向文档即可）
- 让更多人能帮助你

### 写下项目愿景

在 README 或 VISION 文件中明确项目的目标和方向：
- 防止范围蔓延（scope creep）
- 帮助你判断哪些 Feature Request 应该接受

### 明确你的期望

应该写下的规则：
- 贡献如何被审查和接受（需要测试吗？需要 Issue 模板吗？）
- 你接受哪些类型的贡献
- 回复的时间预期（如 "维护者会在 7 天内回复"）
- 你在项目上投入的时间（如 "我每周只花约 5 小时在这个项目上"）

### 保持沟通公开

- 所有关于项目的讨论都应在公开渠道进行
- 私下做出的决定也要在公开场合记录
- 这样任何新加入的人都能获取与老成员相同的信息

## 学会说"不"

### 为什么要说不

说"不"是维护者最重要也最困难的技能：
- 不符合项目范围的功能请求
- 偏离讨论主题的人
- 质量不达标的贡献

### 如何友好地拒绝

1. **感谢** — 感谢对方的贡献和时间
2. **解释** — 说明为什么不符合项目方向，提供改进建议
3. **引用** — 指向相关文档
4. **关闭** — 及时关闭不会接受的 Issue/PR

**模板**：
> Thank you for this contribution! However, this doesn't align with our project's current scope. We're focused on [X], and this would be better suited for [Y]. I'm going to close this, but please feel free to work on this in a fork.

### 关键原则

- "不"是暂时的，"是"是永远的
- 不接受贡献 ≠ 不接受这个人
- 不要因为愧疚而搁置 — 一个积压的 Issue/PR 队列比直接拒绝更令人沮丧
- 越练习说"不"，就越容易

## 善用社区力量

### 分担工作

- 使用 `good first issue` 标签标记简单任务
- 给予持续贡献者更多责任
- 文档化如何升级为 Maintainer

### 让别人来构建

- 鼓励 Fork 和插件化
- 提供 API 和 Hook，让用户自行满足需求
- 当项目足够大时，将它从"工具"转化为"平台"

### 传递控制权

如果需要离开项目：
- 寻找愿意接手的人
- 交出管理权限
- 如果有活跃的 Fork，可以从原项目链接过去

## 自动化一切可自动化的

### 自动化测试

- 为所有 PR 配置 CI（GitHub Actions）
- 设置必须通过测试才能合并
- 这是保证代码质量的最低防线

### 自动化工具推荐

| 工具 | 用途 |
|------|------|
| **GitHub Actions** | CI/CD、自动化工作流 |
| **semantic-release** | 自动化版本发布 |
| **Dependabot** | 自动更新依赖 |
| **Danger** | 自动化代码审查规则 |
| **Stale Bot** | 自动关闭不活跃的 Issue |
| **All Contributors** | 自动记录贡献者 |

### Issue 和 PR 模板

创建 `.github/ISSUE_TEMPLATE/bug_report.md`：

```markdown
---
name: Bug Report
about: Report a bug to help us improve
---

## 描述

简述发生了什么

## 复现步骤

1. ...
2. ...
3. ...

## 期望行为

描述你期望发生什么

## 实际行为

描述实际发生了什么

## 环境信息

- OS:
- Version:
- Browser:
```

## 预防 Burnout

### 认识到 Burnout 的信号

- 对项目感到逃避或内疚
- Issue 和 PR 越积越多让你焦虑
- 对社区互动感到疲惫

### 如何应对

1. **设定边界** — 明确工作时间，不在周末处理
2. **休假** — 定期休息，提前告知社区
3. **寻找帮助** — 培养 Co-maintainer
4. **适时放手** — 如果不再有热情，传递给他人

### 可持续维护的关键

- 你的快乐是项目存活的前提
- 健康的维护者 = 健康的项目
- 设定合理期望，坚守边界
